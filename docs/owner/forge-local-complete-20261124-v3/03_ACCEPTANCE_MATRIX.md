# Complete product acceptance matrix

## What this release accepts

Accept the FORGE product and its no-code localhost operation. The owner will later pull `main` at home and test system flows. Do not make CA-EWS training, a medical application or any other prototype product an acceptance gate for this round.

Developer verification is required before handoff. Home UAT is a separate record for the owner's machine, accounts, desktops and full workflows. Small labelled fixtures can test engineering behavior; they cannot prove a live provider, cloud job or native desktop worked.

## Status and evidence

Track **implementation** and **verification** separately for each criterion and integration. Use `NOT_STARTED`, `IN_PROGRESS`, `IMPLEMENTED` or `BLOCKED` for implementation; use `NOT_RUN`, `PASSED` or `FAILED` for each developer/home check. A blocker states the missing dependency and exact affected operation. An uninspected checkout remains unknown, not automatically implemented or absent.

Record code paths, revision, executed command/action, observed result, environment/target and reproduction steps. Attach useful screenshots and run/artifact records where relevant; redact secrets. Historical results and fixtures retain their actual scope.

## Release assessment

Maintain a coverage row for every requirement, not just completed screens. The integration ledger must distinguish usable implementation from a catalog entry, installed dependency, signed-in account and live qualification. A disabled placeholder with a helpful message is still missing implementation.

The v3 protocol, office and reporting criteria A21–A30 add to A00–A20; they do not replace existing AI engineering, multi-bot, storage, desktop or adaptation requirements. Follow [the AG-UI contract](10_AGUI_HARNESS_PROTOCOL.md), [Univer research](reference/research/UNIVER_INTEGRATION_RESEARCH.md), [report-engine research](reference/research/REPORT_ENGINES_RESEARCH.md) and [model-discovery research](reference/research/T3_MODEL_DISCOVERY_RESEARCH.md). Research findings are implementation inputs, not passed runtime checks. GPT-6.2 availability is not a product-release prerequisite.

Use release-level labels with a stated evidence scope:

- **`IMPLEMENTATION_INCOMPLETE`** when any required local feature or adapter behavior is missing. List the exact gaps and continue executable work.
- **`IMPLEMENTATION_COMPLETE`** only when requested product behavior is implemented and traced to acceptance criteria. This alone does not claim every external service has been exercised.
- **`DEVELOPER_VERIFIED`** only for the named checks and environments that passed. A Linux build does not establish Windows launcher success.
- **`READY_FOR_HOME_UAT`** when implementation, developer checks and delivery instructions are accounted for and target-specific pending checks are explicit. It must not conceal known failing core flows or missing functionality.
- **`HOME_UAT_NOT_RUN`**, **`HOME_UAT_PASSED`** or **`HOME_UAT_FAILED`** records the later owner test independently. Pushing main does not pass UAT.

If unavailable credentials or hardware prevent live qualification, record `NOT_RUN` with the required home setup action. If a provider contract prevents implementation, record an implementation blocker rather than claiming complete support. Do not add an approval gate for every ordinary task; continue work that does not depend on the blocker.

## Verification scope

Test real risks: persistence, synchronized state, task/session identity, cancellation, reconnect, transfer integrity, secret boundaries, native-control ownership and startup portability. Exercise the owner-facing controls. Reuse relevant tests and broaden only to resolve a concrete risk; avoid count-based tests that mirror implementation.

Home UAT may validate full flows after pull, as requested. Before delivery, developers still build, start and inspect the product with available safe engineering inputs. Do not defer every test to the owner or launch a prototype product merely to obtain test evidence.
