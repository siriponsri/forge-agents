Core architectural objectiveStrengthen FORGE's Adaptive Harness through a modular, plugin-oriented architecture inspired by DeepSeek Harness.Preserve the existing FORGE requirements, T3-based GUI, AG-UI protocol, MCP integration, Univer Office, WordCraft/PdfCraft Report Studio, dynamic staffing, local-first runtime, and independent QA.FORGE must remain the sole authority for project planning, task allocation, provider/model routing, acceptance criteria, evidence, and release decisions.Avoid introducing a second independent project planner or competing task database.## 3. Additional implementation tasks### DH-01 — Plugin-oriented capability architecture [P0]- Study Cordis and DeepSeek Harness's everything-is-a-plugin architecture.- Implement or extend FORGE's existing capability registry using typed service contracts, providers, consumers, dependency declarations, and lifecycle management.- Support enable, disable, configuration, compatibility checks, health checks, and safe disposal.- Implement a functional Plugin Manager within the existing Settings GUI.- Prefer incremental integration with existing code over a framework rewrite.- Evaluate Cordis reuse, selective component reuse, or native implementation and document the decision.- Never automatically execute newly discovered third-party plugins.### DH-02 — Scoped Adaptive Harness [P0]- Introduce project, session, agent, and task capability scopes where not already implemented.- Resolve skills, MCP tools, execution environment, model capabilities, and permissions based on actual task requirements.- Assemble model-visible instructions and permitted tool schemas dynamically.- Ensure backend authorization is enforced independently of tool visibility.- Retain provider-native authentication, context, and configuration boundaries.- Record the selected harness configuration and concise selection rationale in the execution receipt.### DH-03 — Durable Session and Event Architecture [P0]- Study DeepSeek Harness session logs, turn/step lifecycle, durable events, transient stream events, and replay projections.- Extend the existing FORGE event and persistence system rather than creating a competing source of truth.- Correlate project, task, agent, session, run, attempt, message, and tool-call identities.- Integrate durable and transient events with the existing AG-UI bridge.- Support reload, restart, cancellation, interrupted-run recovery, and reconciliation.- Replay must not execute tools or repeat external side effects.- Persist only authorized content; redact credentials and do not collect hidden chain-of-thought.- Distinguish recovered conversation state from recovered external process state.### DH-04 — Context Management and Compaction [P0]- Study dsh-compaction, system-prompt assembly, token-meter, spill storage, and session-reference components.- Implement provider-aware context budgets and token accounting.- Preserve owner requirements, acceptance criteria, decisions, critical errors, task state, and artifact references across compaction.- Store large permitted tool outputs outside active model context and provide scoped retrieval handles.- Preserve provenance and original evidence independently of summaries.- Respect native harnesses that own their internal context; use adapter capability negotiation instead of assuming access.- Add deterministic tests demonstrating that compaction preserves critical requirements and does not bypass approval boundaries.### DH-05 — Goal-driven Agent Execution [P0]- Extend existing goal/task contracts with durable goal revisions, continuation policy, progress evaluation, blockers, pause/resume, cancellation, and stopping conditions.- Support repeated execution and adaptation until measurable acceptance criteria are satisfied.- Continue independent safe tasks when another task is blocked.- Enforce configurable attempt, token, spending, and elapsed execution limits.- Prevent infinite loops, duplicate dispatches, and repeated unchanged failures.- Require actual verification evidence before marking a goal complete.- Preserve independent QA and owner approval boundaries.### DH-06 — Agent Team Coordination [P1]- Study DeepSeek Harness Agent Teams and subagent lifecycle.- Extend the existing FORGE task DAG and Team Room with explicit ownership, revision-aware updates, dependency validation, agent messaging, and task handoffs.- Prevent dependency cycles and duplicate task claims.- Enforce isolated worktrees and scoped write authority for parallel coding agents.- Treat advisory write-scope warnings as warnings, not security boundaries.- Project the canonical task state into the existing Kanban and visual planning GUI.- Do not build a competing task board or orchestrator.### DH-07 — Optional DeepSeek Harness Adapter [P1]- Evaluate the official TypeScript SDK, @deepseek-ai/dsh-sdk-client, SDK profile, and stdio JSON-RPC protocol.- Implement a bounded FORGE execution adapter if runtime and integration qualification succeeds.- Keep the adapter disabled by default until verified.- Use a separate DSH_HOME and isolated workspace.- Pin compatible SDK/runtime versions.- Normalize runtime notifications into FORGE events and AG-UI projections.- Support discovery, health checks, scoped dispatch, result collection, cancellation, session restoration, process cleanup, and typed failures as supported by the SDK.- Bind approvals to exact operations through FORGE's authority and verify client-owned approval behavior.- Disable uncontrolled plugin installation, background automation, and unapproved access expansion.- Do not require DeepSeek API credentials or paid calls merely to run the FORGE application.- Do not silently substitute another harness after an external dispatch may already have executed.- Record unsupported capabilities accurately.### DH-08 — Provider and Model Discovery Improvements [P0]- Study DeepSeek Harness's adapter-owned model selection and reasoning capability architecture.- Reconcile this with FORGE's existing model registry and v3 T3 model diagnostic requirements.- Distinguish provider-reported models, locally configured models, stale cached models, and successfully verified live routes.- Preserve the original observation timestamp when refreshing cached or research-derived information.- Do not hardcode GPT-6.2 or DeepSeek model availability.- Distinguish catalog timeout from actual model unavailability.- Display exact model IDs, supported reasoning options, capabilities, source, freshness, and discovery errors in the GUI.- Allow development to continue using existing working models.### DH-09 — Verification and Safety [P0]- DeepSeek Harness is developer-preview software and is not an audited security boundary.- Review SAFETY.md and current platform-specific sandbox limitations.- Qualify optional execution adapters in an isolated environment before enabling them.- Test permission enforcement, workspace isolation, credential isolation, plugin disposal, cancellation, retry behavior, stale state, and restart recovery.- Test malformed tool requests and untrusted content.- Separate deterministic fixtures, real runtime checks, and live model evaluations.- Use actual artifacts and execution receipts as evidence.- Do not transfer private files, credentials, or restricted datasets to external providers without authorization.- Preserve previous successful regression tests.## 4.
