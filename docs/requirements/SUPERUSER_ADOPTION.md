## Product adaptation

| Source concept | FORGE behavior and existing owner |
|---|---|
| Size and brief before dispatch | Versioned five-part brief: objective, inputs/scope, acceptance, interfaces/dependencies, risks/decisions. A no-code workflow preset materializes canonical Mission/Plan/Tasks only on an explicit Owner action. |
| Loop / Graph / Dynamic patterns | Named reviewable presets describing ordered, independent or bounded adaptive work. Reuse Goals, Assistance/Adaptive, Parallel and live Visualization; no second provider runtime or task database. |
| Fresh reviewer and adversarial panel | Explicit review records linked to exact run/attempt/artifact/checksum and reviewed revision. Reviewer findings are evidence; only existing QA/Owner actions can accept delivery. |
| Model scorecard | Use exact observed provider/model/options and measured evidence. Owner-configured roles/ranks remain in Assistance. No universal benchmark, invented prices or archived model-name fallback. |
| Lessons after work | Draft procedural memories linked to actual evidence, followed by existing Adaptive evaluation/promotion. No direct skill rewrite or automatic promotion. |
| Owner style capture | Central private Owner Memory with explicit revision grants to named projects. No hidden cross-project preference sharing. |
| Decision/flag logs and handoff | Persist choices, unresolved questions, next executable action and evidence scope in canonical events; keep unknown results distinct from failure/success. |
| Independent slices and merge | Each development worker uses its own branch/worktree; lead integrates contracts and verifies the application. Product Parallel uses its existing guarded Git queue. |

## Concrete implementation task

Add a first-party Workflow Presets surface, compiled trusted presets and durable
workflow/brief/review/lesson references. Default presets should cover software
delivery, research with sources, independent split-and-merge, review/critique and
bounded improvement. The software flow is the primary acceptance journey.

Use canonical `events`/`receipts`; no migration or shadow task store. Bind exact
Mission/Goal/run/attempt/evidence IDs. A preset instantiation creates a draft and
may call the existing Mission create API with an explicitly reviewed definition.
It must not approve plans, start runs, select arbitrary models, create paid
resources, broaden tool permissions or push Git branches. Review submissions
cannot forge execution or Owner acceptance. Lessons enter existing Memory and
Adaptive gates only as drafts. All HTTP operations require the private Owner
session/CSRF and opaque caller; expose a bounded method allowlist.

Persist preset/version/source provenance and exact operation replay. Test actual
SQLite restart, project isolation, stale revisions, unresolved decision gates,
Mission linkage/no execution on preset selection, evidence revision/tamper
behavior and lessons remaining drafts. Mount the real TH/EN GUI and verify the
combined flow, then include real media in the final English README.

## Deliberate adaptations

Archived `opus`/`sonnet`/`haiku` role defaults and numerical account capacities
are examples, not observed FORGE entitlements. The actual connected catalog and
explicit Owner ceilings win. Automatic Git in a preset cannot expand the final
release authorization. External messages still require explicit session scope;
mobile work retains originating Telegram approval. Stop/review round limits
must retain durable unknown outcomes rather than restart effects to obtain a
green result. Do not add unconditional new approval questions for reversible work.

Development adopts brief → scoped implementation → actual checks → fresh review
where warranted → fix/recheck → evidence-based handoff. Central progress has one
lead writer. Review claims retain their real scope and cannot declare Home UAT.
